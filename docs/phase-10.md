# Phase 10 — ذكاء المخزون (Inventory Intelligence)

> **الحالة:** جاهزة لمراجعة بوابة G2. **الفرع:** `arena/8ae97403-ksslla-commerce-ai`. **لا نداءات Salla جديدة، ولا كتابة، ولا هجرات، ولا AI.**

## 1. الهدف

تُجيب هذه المرحلة عن سؤال واحد: **ما حال المخزون المحفوظ في النسخة المحلية الآن، وما الذي لا يمكن قوله عنه؟**

تغطية الكتالوج بالمخزون، وعدد المتوفر والمنخفض والنافد وغير المحدود، ودرجة صحة وصفية، ومشكلات مرتّبة، وتوصيات استشارية، وتصنيفات بأعدادها — كل ذلك من جدول `inventory_levels` القائم (ADR-043) بلا أي كتابة ولا نداء مزوّد.

### 1.1 معيار الخروج (بوابة G2)

معيار المرحلة من `docs/roadmap.md`: **«لا كتابة مخزون، دقة النموذج موثقة بحدودها، G2»**. وبوابة G2: **«تحليلات قابلة للتفسير ومطابقة للمصدر»**.

كيف تُحقَّق هنا:

| الشرط | ما يثبته التنفيذ |
|---|---|
| لا كتابة مخزون | خمسة مسارات `GET` فقط؛ اختبار تكامل يفحص تصدير الوحدات ويؤكد غياب `POST`/`PUT`/`PATCH`/`DELETE` |
| دقة النموذج موثقة بحدودها | كل مقياس `value/availability/basis/reason`، والأربعة المستحيلة معلنة في `UNAVAILABLE_BY_DESIGN` وفي الواجهة |
| قابلة للتفسير | القاعدة والمعادلة والحدود والنسب مرفقة بالحمولة؛ ترتيب حتمي قابل لإعادة الحساب يدويًا |
| مطابقة للمصدر | الحقول المقروءة هي حقول `List Products Quantities` الموثّقة حصرًا (§5) |

## 2. النطاق

**داخل النطاق:** تغطية المخزون، حالة الكمية (متوفر/منخفض/نافد/غير محدود/غير معروف)، الكمية المرتفعة كملاحظة محايدة، درجة صحة، مشكلات مرتّبة، توصيات قواعدية، تصنيفات بأعدادها، طبقة جودة بيانات، منهجية عربية.

**خارج النطاق (مقصود وموثّق):**

- **لا كتابة مخزون:** لا تعديل كمية، لا تسوية، لا حذف، لا إنشاء صف، ولا نقطة Salla للكتابة.
- **لا نداء Salla جديد:** المصدر هو ما حفظته Phase 05 من `GET /products/quantities` (§5).
- **لا سجل تاريخ مخزون ولا هجرة:** ADR-043 قائم؛ إضافة لقطات دورية تحتاج قرار مالك.
- **لا معدل طلب:** لا من `sold_quantity` التراكمي، ولا من بنود الطلب (بلا معرّف منتج).
- **لا تنبؤ نفاد ولا راكد ولا فائض ولا كمية إعادة طلب** كأرقام — العقود معرّفة ومختبرة ومُعطّلة (ADR-057).
- **لا AI/LLM** ولا توصية مولّدة: كل نص ثابت مربوط بقاعدة.
- **لا Redis/Elasticsearch/Kafka/خدمات مصغّرة.**

## 4. عقد الاستجابة

كل استجابة تحمل المغلّف نفسه، حتى يعرف القارئ على أي بيانات حُسب الرقم:

```json
{
  "storeId": "…",
  "generatedAt": "2026-10-23T…Z",
  "freshness": { "syncedAt": "…", "resources": [...], "staleResources": [...] },
  "coverage": {
    "status": "complete|partial|empty",
    "productsTracked": 4, "productsTotal": 5,
    "coveragePercent": { "value": 80, "availability": "available", "basis": "…", "reason": null },
    "inventoryEntries": 6, "unlinkedEntries": 1,
    "lastSyncedAt": "…", "notes": ["products_without_inventory_record", "inventory_entries_unlinked"]
  },
  "confidence": { "level": "high|medium|low", "inventorySynced": true, "syncFailed": false, "stale": false, "coverageStatus": "partial" },
  "data": { … }
}
```

كل مقياس رقمي داخليًا:

```json
{ "value": 7, "availability": "available|partial|unavailable", "basis": "…", "reason": null }
```

**قاعدة الصفر:** `value = 0` لا يظهر إلا إذا كان الصفر مقيسًا فعلًا (منتج موجود بكمية صفر). غياب المصدر ⇒ `value: null` + `availability: "unavailable"` + `reason`.

## 5. المصادر والتحقق

- **النقطة:** `GET /admin/v2/products/quantities`، النطاق `products.read` — موثّقة ومستخدمة منذ Phase 05.
- **الحقول المقروءة:** `id`, `name`, `sku_id`, `sku`, `quantity`, `sold_quantity`, `price`, `unlimited_quantity`, `variant` — وهي نفس حقول `inventory_levels` المحفوظة.

التحقق الكامل في `docs/salla-reference.md` §18. أهم ثلاث نتائج:

1. **لا ختم زمني ولا فترة في الاستجابة** ⇒ `sold_quantity` تراكمي فقط، ولا يُحوَّل إلى معدل.
2. **`sku_id = null` للمنتج بلا متغيّرات، وصفّ لكل متغيّر** ⇒ مقياس المنتج يجمع صفوفه (6 + 1 = 7).
3. **`unlimited_quantity: true` قد يأتي مع `quantity: 0`** ⇒ «غير محدود» يتقدّم على الرقم.

## 6. حالة المخزون (`stock.ts`)

الترتيب هو القاعدة كلها:

| # | الشرط | الحالة |
|---|---|---|
| 1 | `unlimited_quantity = true` | `unlimited` |
| 2 | `quantity <= 0` | `out_of_stock` |
| 3 | `quantity <= 5` | `low_stock` |
| 4 | غير ذلك | `in_stock` |

- لا صف مخزون للمنتج ⇒ `unknown` (يقرّره المستدعي الذي يعرف وجود الصف). لا تُقرأ `0` أبدًا.
- الكمية السالبة `out_of_stock` + مشكلة `negative_quantity` عالية؛ لا تُقصّ إلى صفر لأن القصّ يخفي عيب البيانات.
- `highStockQuantity` = `!unlimited && quantity >= 50` — **ملاحظة كمية محايدة**، لا تُسمّى راكدًا ولا فائضًا.

## 7. التغطية (`catalog.ts`)

`التغطية = منتجات لها سجل مخزون ÷ إجمالي المنتجات`

| الحالة | النتيجة |
|---|---|
| لا منتجات | `unavailable("no_products_stored")` |
| منتجات بلا أي صف مخزون ومزامنة نجحت | `unavailable("no_inventory_rows")` |
| منتجات بلا أي صف ومزامنة لم تحدث | `unavailable("inventory_not_synced")` |
| صفوف موجودة لكن المزامنة غير مسجّلة | `partial` + `"inventory_not_synced"` |
| تغطية أقل من 100% | `status: partial` + `products_without_inventory_record` (القيمة الحقيقية مثلًا 80، لا تُقرَّب إلى 100) |
| كاملة | `complete` |

`notes` تحمل أيضًا: `inventory_sync_incomplete`, `inventory_entries_unlinked`, `inventory_snapshot_stale`. **التغطية لا تكون 100% أبدًا عند نقص السجلات**، ولا تُستخدم لتقدير كمية منتج مفقود.

## 8. درجة الصحة

```
score = 25 × (تغطية%) + 35 × (متوفر% بين المعروف)
      + 20 × (100 − منخفض%) + 20 × (100 − نافد%)
```

- `unavailable("no_products_stored")` عند غياب الكتالوج، و`unavailable("inventory_not_synced")` عند غياب المخزون والمعروف صفر.
- `partial` عند تغطية < 100% (`inventory_coverage_partial`) أو وجود كمية سالبة (`negative_quantity_present`).
- **وصفية لحالة الرف الآن؛ ليست توقع مبيعات ولا مؤشر أداء**، والحدود الخمسون/الخمسة معلنة في `thresholds.ts`.

## 9. الطلب (`demand.ts`)

`resolveDemand()` لا يأخذ معاملات ويعيد دائمًا:

```json
{ "dailyDemand": { "value": null, "availability": "unavailable", "basis": "…", "reason": "product_demand_not_linked" } }
```

سببان مستقلان وموثّقان: بنود الطلب بلا معرّف منتج (Phase 05)، و`sold_quantity` بلا فترة (§5). عقد `DemandInput { unitsPerDay, windowDays, source }` معرّف للمستقبل وموصول بلا شيء.

## 10. الأيام المتبقية (`daysOfStockFrom`)

`الأيام = الكمية ÷ الطلب اليومي`، بدقة منزلة واحدة. الدالة **كلية**:

| المدخل | النتيجة |
|---|---|
| طلب غير متاح | `unavailable(product_demand_not_linked)` |
| طلب `NaN`/`∞`/سالب | `unavailable("invalid_demand")` |
| طلب صفر | `unavailable("no_demand_in_window")` — لانهائية ليست رقمًا |
| كمية غير محدودة | `unavailable("unlimited_stock")` |
| غير ذلك | `available(quantity ÷ demand)` |

**الوضع الحالي:** كل منتج `—` + `product_demand_not_linked`. هذا هو السلوك الصحيح لا الفشل.

## 11. التنبؤ بالنفاد (`stockout.ts`)

النطاقات معرّفة: `≤ 3` حرج، `≤ 7` تحذير، `≤ 14` مراقبة، أكثر من ذلك طبيعي — والحدود **شاملة للحد الأدنى** (3 أيام = حرج). كل نطاق مبني على `daysOfStock` فقط، لأنه لا يوجد طريق آخر يفسّر الدالة عند حدوده.

في التشغيل: `daysOfStock` غير متاحة دائمًا ⇒ `stockoutRisk = "unknown"` + سبب. لا خطر من الكمية وحدها: 3 وحدات ليست حرجة إن كان المنتج يُبيع مرة في الشهر.

## 12. الفائض والراكد وإعادة الطلب

**الفائض/الراكد (`excess.ts`):**

- `highStockQuantity` نشط (ملاحظة محايدة).
- `deadStock` و`excessInventory` غير متاحين: يحتاجان معدل طلب ونافذة مراقبة. `updated_at` للمنتج **ليس** بديلًا — تعديل المنتج لا يقول شيئًا عن بيعه.

**إعادة الطلب (`reorder.ts`):**

```
reorderQuantity = max(0, ceil(dailyDemand × (leadTimeDays + safetyStockDays) − availableStock))
```

المدخلات الثلاثة ناقصة دائمًا: `product_demand_not_linked`, `lead_time_not_configured`, `safety_stock_not_configured`. تُعاد **كلها** في تمريرة واحدة عبر `reorderMissingInputs`، مع `unavailable`. النموذج نفسه مختبر حدوده (تقريب لأعلى، أرضية صفر، رفض الكمية غير المحدودة).

## 13. المشكلات والترتيب (`issues.ts`)

خمس قواعد، كل واحدة بمجموعتها الخاصة (منتجات أو سجلات):

| id | الخطورة | القاعدة | المجتمع |
|---|---|---|---|
| `out_of_stock` | عالية | `quantity <= 0 AND unlimited_quantity = false` | منتجات |
| `negative_quantity` | عالية | `quantity < 0` | منتجات |
| `low_stock` | متوسطة | `0 < quantity <= 5 AND unlimited = false` | منتجات |
| `missing_inventory_record` | متوسطة | لا صف مخزون مرتبط بالمنتج | منتجات |
| `inventory_entry_unlinked` | منخفضة | `product_id IS NULL` | سجلات مخزون |

**الترتيب حتمي:** `score = affected × weight(3/2/1)`، ثم الخطورة، ثم العدد، ثم المعرّف. نفس اللقطة ⇒ نفس الترتيب، والقارئ يستطيع إعادة حسابه.

كل صف يحمل `rule` و`definition` و`evidence` (حتى ثلاثة أسماء منتجات) — دليل قابل للفتح لا رقم بلا مصدر.

## 14. التوصيات (`recommendations.ts`)

- واحدة لكل **مشكلة أطلقت**، ولا شيء لغيرها.
- `{ id, issueId, title, priority P1/P2/P3, severity, rationale, rule, affectedCount, affectedPercent, evidence, advisoryOnly: true }`.
- النص لا يحتوي «اطلب N وحدة»، ولا «سينفد خلال N يومًا»، ولا «راكد»: الجملة لا تدّعي نموذجًا غير عامل.
- `advisoryOnly` حرفي `true`، ولا مسار تنفيذ في الوحدة.

## 15. التصنيفات (`categories.ts`)

مجموع منتجات التصنيف وحالاتها (`inStock`, `lowStock`, `outOfStock`, `unlimited`, `unknownCount`, `highStockQuantity`)، ونِسَب المتوفر/النافد، وتغطية التصنيف — **كتالوج لا مبيعات**: لا معدل طلب ولا دوران (`demandRate = unavailable`). تصنيف بلا منتجات يعطي `unavailable("no_products_in_category")` لا 0%.

## 16. واجهات API

الخمسة تحت `/api/organizations/current/stores/[storeId]/inventory-intelligence/`، وكلها `GET` فقط:

| المسار | الحمولة |
|---|---|
| `overview` | النظرة العامة، الأعداد، المشكلات، أفضل 5 توصيات، التعريفات، الحدود وتسمياتها، وغير المتاح بالتصميم |
| `products` | صفحة منتجات (`page`, `pageSize ≤ 100`, `q`, `filter`) + المجموع وعدد الصفحات |
| `categories` | صحة مخزون كل تصنيف |
| `issues` | كل المشكلات المرتّبة |
| `recommendations` | التوصيات الاستشارية (`advisoryOnly: true`) |

المرشّحات: `all`, `out_of_stock`, `low_stock`, `in_stock`, `unlimited`, `unknown`, `high_quantity`. معاملات غير صالحة (`page=0`, `pageSize=101`, `filter=nope`, `q` > 120) ⇒ **422** عبر `AppError VALIDATION_FAILED`.

**لا `period` ولا `asOf`:** لا تاريخ مخزون لتصفيته؛ المعاملان يُتجاهلان أصلًا واختبار الوحدة يثبت ذلك.

## 17. قاعدة البيانات والهجرات

- **صفر هجرات.** `inventory_levels` و`products` و`categories` و`product_categories` تكفي.
- القاعدة (ADR-043) لم تُمس: جدول حالة حالية بمفتاح فريد `(store_id, quantity_key)`، يُحدَّث ولا يُلحق.
- لا جدول مشتقات ولا كاش ولا مادة ملخّصة (ADR-053).
- `last_synced_at` على الصف هو «حتى متى؟»، ويظهر في الواجهة؛ لا يُشتق منه معدل.

## 18. الواجهة

`/app/stores/[storeId]/inventory-intelligence` — عربية RTL، والأقسام بالترتيب المطلوب:

1. **شريط جودة البيانات:** التغطية، الثقة، آخر مزامنة، وكل `notes` بالعربية؛ رسالة صريحة «لم تتم مزامنة بيانات المخزون بعد» عند الغياب.
2. **نظرة عامة:** إجمالي المنتجات، التغطية، المتوفر، المنخفض (≤ 5)، النافد، غير المحدود، بلا سجل، درجة الصحة، إجمالي الوحدات، الكمية المرتفعة (≥ 50)، الكميات السالبة، عدد السجلات وغير المرتبطة، ثم **الأيام المتبقية/الراكد/إعادة الطلب = «—» + سبب**.
3. **المخاطر:** جدول المشكلات (القاعدة، الخطورة، المتأثرون والنسبة والمجتمع، الدرجة، أمثلة)، مع سطر يوضح أن نطاقات النفاد (3/7/14) معرّفة ولا تُفعّل.
4. **المنتجات:** المنتج | المخزون | الحالة | التغطية | الأيام المتبقية | المخاطر — كل خلية غير متاحة تحمل «—» + سببها. بحث بالاسم/SKU، وسبعة مرشّحات، وترقيم صفحات.
5. **التصنيفات:** الأعداد والنِسَب والتغطية، ومعدل الطلب «—».
6. **التوصيات:** بطاقات استشارية بالقاعدة والأمثلة، وحد أقصى 5.
7. **«كيف نحسب هذه الأرقام؟»:** تعريف كل مؤشر، الحدود وقيمها، وما لا يمكن قياسه ولماذا.

أُضيفت بطاقة رابعة في صفحة المتجر. لم يُضف رابط في الشريط العلوي، لأن صفحات التحليل مرتبطة بمتجر واحد — كما في Phase 07/08/09.

`REASON_LABELS_AR` اكتسبت 15 تسمية جديدة، فلا يظهر معرّف إنجليزي في الواجهة.

PostgreSQL حقيقي + محاكي Salla، والمخزون يصل عبر **مسار المزامنة الحقيقي** (OAuth → كتالوج → مزامنة مخزون → mappers → repositories):

- لقطة كاملة: تغطية 4/5 = 80%، ستة سجلات، سجل غير مرتبط، الأعداد الأربعة، الوحدات 90، والمشكلات الأربع بترتيبها.
- تجميع المتغيّرات: 6 + 1 = 7 لمنتج واحد.
- متجر بلا أي مزامنة: `empty` + `no_products_stored`/`inventory_not_synced`، بلا أصفار.
- كتالوج مُزامَن بلا مخزون: خمسة `unknown`، `missing_inventory_record` فقط.
- غير محدود بكمية صفر: `unlimited` بلا مشكلة.
- الترقيم والبحث والمرشّحات السبعة، وتثبيت `page=99` على آخر صفحة.
- التصنيفات: أعداد، تغطية 66.7 و100، `demandRate` غير متاح.
- التوصيات: أربع، كلها `advisoryOnly` ومربوطة بمشكلاتها.
- اتساق اللقطة: نفس الأعداد والتغطية والترتيب بين endpoints.
- الأمان: 401 بلا جلسة، 404 لمستأجر آخر، مشاهد يقرأ بلا حقول هوية، 422 لكل معامل غير صالح، `TENANT_ISOLATION_VIOLATION` عند مؤسسة أخرى.
- **فحص بنيوي للقراءة فقط:** الوحدات الخمسة تصدّر `GET` ولا تصدّر أي من `POST`/`PUT`/`PATCH`/`DELETE`.
- **اختبار انحدار التنبؤ:** يمرّ على حمولة المسارات الخمسة كاملة ويفشل إن حمل أي مفتاح تنبؤي (`daysOfStock`, `deadStock`, `reorderQuantity`, `excessInventory`, `demandRate`, `dailyDemand`) رقمًا بدل `null` + سبب.
- الكمية المرتفعة لا تُنتج `dead_stock` ولا `overstock`.

## 20. الأمان

- **السلسلة:** الجلسة → المؤسسة → العضوية → `store:read` → `requireStoreAccess` → `withTenantTransaction` (RLS جدار ثانٍ).
- `storeId` يأتي في المسار لكنه يُتحقق منه؛ `organizationId` لا يُقبل من العميل.
- الحمولة خالية من الهوية: لا بريد ولا هاتف ولا اسم عميل ولا رموز.
- **قراءة فقط بنيويًا:** لا عميل Salla في الوحدة، ولا زر تنفيذ، ولا مسار كتابة. رؤوس الأمان وCSRF والجلسات لم تُمَس.
- لا PII في أي مستودع مخزون: الحقول المنقولة أسماء منتجات وSKU وكميات فقط.

## 21. الأداء

- **4 استعلامات مجمّعة** لكل طلب: منتجات المتجر (إسقاط ضيق)، روابط التصنيفات، التصنيفات، صفوف المخزون. التجميع في الذاكرة.
- **صفر N+1:** لا استعلام لكل منتج ولا نداء مزوّد.
- مسح جدول `inventory_levels` عبر `store_id` مفهرس، وحجمه محدود بحجم الكتالوج لا بتاريخ المزامنة (ADR-043).
- لا كاش خارجي. إعادة الحساب كل طلب مقبولة لحجم متجر واحد وتُراجع بالقياس.

## 22. القيود والأسئلة المفتوحة

**قيود مقصودة (ليست أخطاء):**

1. لا معدل طلب ⇒ لا أيام متبقية ولا تنبؤ نفاد ولا فائض/راكد ولا كمية إعادة طلب.
2. `sold_quantity` يُعرض تراكميًا كما هو فقط؛ لا نسبة إلى فترة.
3. الكمية المرتفعة ملاحظة لا حكم.
4. `low_stock` حدّ مطلق (5) لا تنبؤ؛ منتج يُبيع ببطء قد يبقى «منخفضًا» طويلًا.
5. التغطية تصف الكتالوج الحالي؛ منتج يُضاف بعد المزامنة يظهر `unknown` حتى مزامنة تالية.
6. لا سجل تاريخ ⇒ لا «نفد سابقًا» ولا «مدة النفاد» ولا «معدل الدوران».
7. بيانات المتجر الحقيقية غير مستخدمة، ولا نداء Salla حيّ في هذه المرحلة (لا نداء جديد أصلًا).

**أسئلة مفتوحة:**

1. هل يوجد مصدر موثّق يُنتج وحدات مبيعة **لكل منتج** في نافذة معلومة؟ إن وُجد، يُفعّل `DemandInput` ويُوثَّق في §18 قبل أي تفعيل.
2. هل يريد المالك ضبط مهلة توريد ومخزون أمان لكل متجر؟ هذا إعداد منتج، لا هجرة بيانات، ويحتاج قرارًا مع حدود افتراضية معلنة.
3. هل تُخزَّن لقطات مخزون دورية؟ ADR-043 يمنعها اليوم لتكلفة غير مبرَّرة؛ القرار يحتاج مُستهلكًا حقيقيًا للناريخ أولًا.
4. هل `inventory_levels` يغطي كل أنواع المنتجات في متجر حقيقي؟ مثال التوثيق يغطي 84 سجلًا لمتجرب واحد؛ يحتاج تحققًا حيًّا قبل G5.
