# Architecture Decision Records (ADRs)

> كل قرار قابل للتغيير، لكن ليس بصمت. أي تعديل يتطلب ADR جديدًا يشير إلى القديم.
>
> **التاريخ الموحّد للقرارات الأولية:** 2026-10-21

---

## ADR-001 — Modular Monolith بدل Microservices

- **الحالة:** مقبول
- **السياق:** مشروع جديد، فريق صغير، يتطلب معاملات متسقة بين الطلبات والمخزون والتحليلات.
- **القرار:** تطبيق Next.js واحد مقسّم إلى وحدات بحدود برمجية، مع Worker منفصل لاحقًا.
- **البدائل:** microservices (رفض: تكلفة تشغيل وتعقيد بيانات عالية)، monolith غير مقسم (رفض: يمنع الفصل المستقبلي).
- **النتائج:** سرعة تطوير، ACID، اختبارات أبسط. التكلفة: انضباط في الحدود يجب مراجعته.
- **إعادة النظر:** عند حاجة وحدة (مثل AI/SEO) إلى توسّع مستقل أو فريق منفصل.

## ADR-002 — Next.js 16 App Router

- **الحالة:** مقبول
- **السياق:** الحاجة إلى واجهة عربية RTL + API + نشر بسيط.
- **القرار:** Next.js 16.4.2 / React 19.3.1 / App Router.
- **البدائل:** SPA + API منفصل (رفض: تعقيد تشغيلي مبكر)، Remix/Astro (رفض: نظام أقل ملاءمة للوحات التفاعلية لاحقًا).
- **النتائج:** RSC يقلل JS، route handlers للـ API، وبيئة معروفة. التكلفة: ارتباط بإيقاع Next.
- **إعادة النظر:** لا متوقع قبل Phase 24.

## ADR-004 — PostgreSQL + Drizzle ORM

- **الحالة:** مقبول (تنفيذ Phase 02)
- **السياق:** بيانات علائقية، JSONB للأحداث، تحليلات، عزل RLS.
- **القرار:** PostgreSQL 16 + Drizzle ORM + Drizzle Kit.
- **البدائل:** Prisma (رفض: محرّك/codegen، وSQL أقل شفافية، وتعقيد نشر)، MongoDB (رفض: علاقات وتقارير)، raw SQL فقط (رفض: سرعة تطوير أقل).
- **النتائج:** SQL صريح، هجرات مقروءة، دعم RLS، بلا محرّك أصلي.
- **إعادة النظر:** لا متوقع.

## ADR-005 — تعدد المستأجرين من اليوم الأول

- **الحالة:** مقبول
- **السياق:** المشروع يبدأ بمتجر واحد (كشخة) لكنه SaaS.
- **القرار:** `User → Organization → Store → SallaConnection` من أول مخطط قاعدة بيانات. متجر واحد لكل مؤسسة الآن، والتصميم يسمح بعدة متاجر.
- **البدائل:** `store_id` مباشر على المستخدم (رفض: يعيد بناء النظام لاحقًا).
- **النتائج:** تعقيد بسيط الآن، عزل حقيقي لاحقًا.

## ADR-006 — لا `store_id` من العميل كدليل صلاحية

- **الحالة:** مقبول
- **السياق:** أشهر ثغرة في SaaS متعدد المستأجرين هي IDOR.
- **القرار:** تحديد المتجر من الجلسة → العضوية → الصلاحية → UUID داخلي. قيمة العميل «طلب» فقط.
- **النتائج:** كل use case يستقبل `TenantContext` إلزاميًا. التكلفة: boilerplate مقصود.
- **الاختبار:** مصفوفة عزل لكل مسار كتابة/قراءة.

## ADR-007 — جلسات مخصّصة Opaque بدل Auth.js Credentials

- **الحالة:** مقبول (تنفيذ Phase 02)
- **السياق:** نحتاج إبطالًا فوريًا، سياق مستأجر واضحًا، ومسار SSO مستقبلًا. Auth.js مع Credentials provider يقيّد جلسات قاعدة البيانات.
- **القرار:** جلسات opaque 256-bit مخزّنة SHA-256 في `sessions`، كوكي `__Host-*`، `scrypt` لكلمات المرور، وتدوير/إبطال كامل.
- **البدائل:** Auth.js + JWT (رفض: إبطال أصعب)، Auth.js + DB sessions مع Credentials (رفض: قيود معروفة)، Clerk/Auth0 (رفض: تكلفة واعتماد خارجي مبكر).
- **النتائج:** تحكم كامل وقابلية اختبار. التكلفة: نحن مسؤولون عن أمان المصادقة؛ تُخفَّف بمراجعة أمنية واختبارات ASVS.
- **إعادة النظر:** عند إضافة SSO/Social login.

## ADR-008 — Salla Custom Mode OAuth مع `state`

- **الحالة:** مقبول مبدئيًا — يتطلب تأكيدًا في Phase 03
- **السياق:** نريد ربط المتجر بمؤسسة محددة يبدأها مستخدم مصادق.

- **البدائل:** Easy Mode عبر `app.store.authorize` (يُعاد تقييمه إن اشترطته Salla للنشر).
- **النتائج:** تحكم بالربط. التكلفة: إدارة تجديد الرموز بأنفسنا.
- **إعادة النظر:** بعد قراءة متطلبات Salla Partners الفعلية.

## ADR-009 — سياسة «لا Endpoint بلا وثيقة»

## ADR-010 — تشفير رموز Salla + تجديد Single-Flight

- **الحالة:** مقبول (تنفيذ Phase 03)
- **السياق:** رموز Salla تمنح وصولًا لمتجر كامل، والـ refresh أحادي الاستخدام.
- **القرار:** AES-256-GCM مع IV فريد وAAD = `store_id` و`key_version`، تجديد استباقي داخل قفل صفّي/موزّع، ومنع التجديد المتوازي.
- **النتائج:** تقليل خطر سرقة الرموز وإبطال الاتصال. التكلفة: تعقيد تشغيلي ودوران مفاتيح.

## ADR-029 — نطاق RLS في Phase 02

- **الحالة:** مقبول ومنفّذ
- **السياق:** `organization_members`, `stores`, `invitations`, `audit_logs` لها مفتاح مستأجر طبيعي. أما `users` و`sessions` فتُقرأ قبل وجود سياق مؤسسة (تسجيل الدخول نفسه)، وليست مملوكة لمؤسسة واحدة.
- **القرار:** تفعيل RLS مع `FORCE` على الجداول الأربعة فقط، وإبقاء `users`/`sessions` محميتين بطبقة التطبيق وتجزئة الرموز، مع إعادة التقييم في Phase 24 (مراجعة أمنية).
- **البدائل:** RLS على كل الجداول عبر سياسات `user_id = current_user`؛ رفضت لأنها لا تعبّر عن الوصول المؤسسي وتُعقّد تسجيل الدخول.
- **الأثر:** لا ندّعي أن RLS وحدها كافية. الاختبارات تُثبت أن دور التطبيق غير مالك ولا يملك `BYPASSRLS`، وأن الكتابة عبر المستأجرين تفشل.

## ADR-030 — صلاحيات Phase 02 الإضافية ونطاق إنشاء المتجر

- **الحالة:** مقبول ومنفّذ
- **السياق:** مصفوفة `docs/phase-02.md` §4.2 تغطي إدارة المتجر والصلاحيات، لكنها لا تحدد صلاحية قراءة/تحديث بيانات المؤسسة نفسها، ولا من ينشئ سجل متجر داخليًا.
- **القرار:** إضافة `organization:read` (لكل الأدوار) و`organization:update` (Owner/Admin فقط)، وإنشاء سجل المتجر الداخلي تحت `organization:update` وليس `store:connect`. نقل الملكية يبقى عملية صريحة غير منفّذة في هذه المرحلة.
- **البدائل:** إضافة `store:create`؛ رفضت لأنها توسّع المصفوفة الموثّقة بلا حاجة.
- **الأثر:** مصفوفة الأدوار المعلنة لم تتغيّر؛ أُضيف صفّان موثّقان في الكود ويُفحصان آليًا مقابل الوثيقة.

## ADR-031 — حماية CSRF: Origin + double-submit

- **الحالة:** مقبول ومنفّذ
- **السياق:** المصادقة بكوكي `HttpOnly` تعني أن أي موقع يمكنه إرسال طلبات تحمل الكوكي.
- **القرار:** كل طلب يغيّر الحالة يمرّ بفحصين: مطابقة `Origin` (أو `Referer` عند غيابه) مع المضيف، ومساواة كوكي `__Host-ksh_csrf` المقروء مع ترويسة `x-csrf-token` ومقارنة زمنية آمنة. `SameSite=Lax` و`HttpOnly` ليستا دفاع CSRF.
- **البدائل:** SameSite فقط؛ رفض لأن المتصفحات القديمة/الوكلاء قد لا تفرضه.
- **الأثر:** العميل يجلب رمزًا من `GET /api/auth/csrf` قبل أول تعديل، ويُجدّد مرة عند 403. الطلبات غير المتصفحية بلا Origin/Referer تُرفض.

## ADR-032 — Rate limiting في الذاكرة حتى Phase 06

- **الحالة:** مقبول ومنفّذ
- **السياق:** لا Redis في البيئة، والنشر الحالي أحادي النسخة.
- **القرار:** واجهة `RateLimiter` + تنفيذ `InMemoryRateLimiter` بحدود: دخول 10/15د لكل IP و5/15د لكل حساب، تسجيل 5/ساعة لكل IP، دعوات 20/ساعة لكل مؤسسة. المفاتيح مجزّأة، والعدادات لا تُسجّل.
- **البدائل:** جدول PostgreSQL للعدادات؛ رفض الآن لأنه يضيف كتابة على كل محاولة دخول.
- **الأثر:** الحدود لكل عملية على حدة؛ عند التوسّع لعدة نسخ في Phase 06 يجب استبدال التنفيذ خلف نفس الواجهة.

## ADR-033 — تسليم الدعوة عبر رابط لمرة واحدة

- **الحالة:** مقبول ومنفّذ
- **السياق:** لا مزوّد بريد ولا أسرار بريد في Phase 02، والخطة تشترط عدم اختراع تكامل.
- **القرار:** يُنشأ رمز عشوائي 32 بايت، يُخزَّن HMAC-SHA256 منه فقط، ويُعاد الرابط مرة واحدة إلى المالك الذي يشاركه. لا `ConsoleEmailSender` ولا طابور بريد.
- **البدائل:** تسجيل الرابط في السجل للتطوير؛ رفض لأن السجلات قد تُجمع.
- **الأثر:** تجربة أقل سلاسة، لكن بلا تسريب بريد لمزوّد غير معتمد. مزوّد البريد يُختار قبل الإنتاج (Phase 25).

## ADR-034 — وضع OAuth: Custom Mode الآن، Easy Mode هدف النشر

- **الحالة:** مقبول ومنفّذ جزئيًا (Custom Mode منفّذ؛ Easy Mode موثّق كاعتماد لاحق)
- **السياق:** وثائق Salla تنص على أن **Easy Mode هو الوحيد المسموح للتطبيقات المنشورة** في Salla App Store، وأن Custom Mode مخصّص «لأغراض الاختبار». Easy Mode لا يعيد التوجيه إلى callback؛ بل تُسلَّم الرموز إلى Webhook `app.store.authorize` بعد تثبيت التطبيق. المرحلة 03 ممنوعة صراحةً من بناء نظام Webhooks.
- **القرار:**
  1. **التطوير/الاختبار (Phase 03):** Custom Mode مع `state` وcallback، لأن الوثائق تصفه صراحةً لهذا الغرض، ولأنه المسار الوحيد القابل للتحقق آليًا دون Webhook.
  2. **الإنتاج:** Easy Mode إلزامي عند النشر في App Store. يُعلن النظام `oauthImplemented=false` عند اختيار `SALLA_OAUTH_MODE=easy` حتى لا يُدّعى تكامل غير موجود.
  3. **المعمارية:** نموذج الاتصال لا يعتمد على الـ callback. كل مسار (callback اليوم، Webhook لاحقًا) يمر عبر نفس دالة الحفظ/التحقق/التدقيق `saveAuthorizedConnection` + `recordAudit`، والعقد الوحيد المطلوب هو «مجموعة رموز + هوية متجر + سكوبات».
- **البدائل المرفوضة:** التنفيذ بـ Easy Mode الآن عبر استقبال Webhook (خارج نطاق المرحلة ويستلزم نظام تحقق توقيع ومكافحة تكرار)؛ أو ادّعاء أن Custom Mode صالح للإنتاج (يخالف نص الوثائق).
- **الأثر:** كل تكامل Phase 03 قابل لإعادة الاستخدام في Easy Mode دون تغيير الجداول أو الواجهة أو منطق التجديد. الفرق الوحيد هو **مصدر** الرموز، ويُضاف في مرحلة Webhooks عبر handler رقيق يستدعي الطبقة نفسها.
- **المصدر:** https://docs.salla.dev/doc-421118، https://docs.salla.dev/421413m0 (المفصّل في `docs/salla-reference.md` §8 صفوف 12–14).

## ADR-035 — نموذج الاتصال وتخزين الرموز والقفل الأحادي للتجديد

- **الحالة:** مقبول ومنفّذ
- **السياق:** الرموز أسرار طويلة العمر (14 يومًا/شهر)، وrefresh token **أحادي الاستخدام**: استخدامه مرتين يُبطل المنحة كلها ويُلزم التاجر بإعادة التثبيت. تخزينها في `stores` يخلط السجل الداخلي ببيانات مزوّد، ويجعل تدوير المزوّد لاحقًا إعادة كتابة.
- **القرار:**
  1. جدول `store_connections` منفصل (organization_id, store_id, provider, status, external_store_id, external_user_id, scopes, ciphertexts, expiries, timestamps) مع قيد فريد `(store_id, provider)` وقيد فريد جزئي `(provider, external_store_id)`.
  2. `stores.status` يبقى انعكاسًا مشتقًا (`connected`/`not_connected`) ولا يحمل أي سر.
  3. تشفير **AES-256-GCM** لكل رمز على حدة، nonce عشوائي 12 بايت لكل قيمة، AAD = `provider|org|store`، مفتاح 32 بايت hex من `ENCRYPTION_KEY` بلا بديل افتراضي.
  4. قفل تجديد في قاعدة البيانات: `refresh_lock_id` + `refresh_lock_expires_at` + `token_version`. من يفوز بالقفل يعيد قراءة الصف، ويتخطى التجديد إن سبقه عامل آخر، ويخزّن الزوج الجديد بشرط `token_version` المتوقع.
  5. `authorization code` لا يُخزَّن ولا يُسجَّل؛ يُستهلك مرة واحدة داخل الطلب.
- **البدائل المرفوضة:** تشفير على مستوى العمود في Postgres (لا يحمي من نسخة احتياطية مسروقة بنفس المفتاح)؛ قفل في الذاكرة (لا يعمل مع أكثر من نسخة)؛ `SELECT … FOR UPDATE` أثناء نداء الشبكة (يحجز اتصالًا ويطيل القفل).
- **الأثر:** إعادة الربط تُحدّث نفس الصف؛ الفصل يمسح الرموز فقط؛ أي تسريب لصف واحد لا يُفكّ إلا بمفتاح البيئة الصحيح ومع AAD الخاص بالمستأجر نفسه. الاختبارات تُثبت: 10 طلبات متزامنة ⇒ تجديد واحد، ولا إعادة استخدام.

## ADR-036 — `state` خادمي مُجزّأ، أحادي الاستخدام، ومربوط بأربعة أبعاد

- **الحالة:** مقبول ومنفّذ
- **السياق:** `state` هو الحماية الوحيدة لـ callback عام لا يحمل جلسة موثوقة من Salla. تخزينه كنص صريح يجعل تسريب قاعدة البيانات كافيًا لاختطاف تدفّق ربط.
- **القرار:**
  1. القيمة 32 بايت من `crypto.randomBytes` (256 بت) بترميز base64url.
  2. يُخزَّن **HMAC-SHA256** منها فقط في `oauth_states.state_hash` (فريد).
  3. مربوطة بـ `user_id` + `organization_id` + `store_id` + `provider`، وعمرها 10 دقائق.
  4. تُستهلك بـ `UPDATE … SET used_at = now() WHERE id = $1 AND used_at IS NULL` — أي محاولة ثانية تفشل بنيويًا وترجع `state_replayed`.
  5. بدء تدفّق جديد يُبطل أي state غير مستخدم لنفس المتجر.
  6. تُقرأ قبل معرفة المؤسسة عبر `app.current_oauth_state_hash()` وسياسة RLS تُظهر الصف المطابق فقط، ثم `bindOrganization()` قبل التحديث.
- **البدائل:** JWT موقّع بلا تخزين (لا يدعم الإبطال ولا الاستخدام الواحد)؛ تخزين في الذاكرة (لا يعمل مع أكثر من نسخة)؛ كوكي فقط (قابل للسرقة مع الجلسة).
- **الأثر:** إعادة تشغيل الطلب أو فتح رابط callback قديم لا ينجح أبدًا، وسرقة الصف لا تمنح قيمة قابلة للاستخدام.

## ADR-037 — تصنيف أخطاء Salla داخل رموز Phase 01، و`/api/health` بلا بيانات مستأجر

- **الحالة:** مقبول ومنفّذ
- **السياق:** نحتاج تمييز فشل Salla (شبكة، استجابة غير صالحة، منحة ملغاة، حد معدل) دون توسيع كتالوج رموز الأخطاء العام كل مرة. وفي الوقت نفسه، `/api/health` عام (بلا مصادقة)؛ عرض حالة اتصال متجر فيه سيكشف نشاط مستأجر لأي زائر.
- **القرار:**
  1. لا رموز جديدة في `AppErrorCode`. تُستخدم `INTEGRATION_NOT_CONFIGURED` (503)، `INTEGRATION_NOT_CONNECTED` (409)، `INTEGRATION_AUTH_REQUIRED` (409)، `INTEGRATION_ERROR` (502)، `RATE_LIMITED` (429) — وهي إضافة موثّقة على الكتالوج.
  2. التمييز الدقيق في حقل داخلي `sallaKind` على `SallaIntegrationError` (`not_configured | authorization | invalid_grant | network | invalid_response | rate_limited | api`) ولا يُسلسَل للعميل.
  3. `/api/health` يعيد `configured`, `oauthMode`, `oauthImplemented` فقط. حالة الاتصال تُقرأ من `/api/organizations/current/stores/{id}` داخل المستأجر.
- **البدائل:** رمز خطأ لكل حالة (`SALLA_*`) — يضخّم الكتالوج ويكسر افتراض «رموز مستقرة»؛ عرض عدد الاتصالات في health — تسريب غير مقبول.
- **الأثر:** أي مراقبة خارجية تعرف «هل التكامل مهيأ» لا «كم متجرًا متصل»، والواجهة تعرض الحالة الدقيقة من مسار مصرّح.

## ADR-038 — نموذج مزامنة الكتالوج: معاملة لكل صفحة، Upsert بالمفتاح الخارجي، وبلا حذف هدمي

- **الحالة:** مقبول ومنفّذ
- **السياق:** المزامنة الأولى لمتجر كبير قد تحمل آلاف المنتجات. تحميل كل الصفحات في الذاكرة ثم الكتابة دفعةً واحدة يضخّم الذاكرة ويجعل أي فشل لاحق يُلغي كل التقدّم. والحذف التلقائي عند غياب عنصر من قائمة غير مضمونة الاكتمال خطر (اختفاء مؤقت في المزوّد ≠ حذف).
- **القرار:**
  1. تُقرأ الصفحات بالتسلسل وتُعالج واحدةً واحدة؛ لا `Promise.all` على قائمة صفحات.
  2. كل صفحة تُكتب في معاملة واحدة: Upsert للصفوف + استبدال روابط تلك الصفحة + تحديث عدّادات التشغيل. لا يُعلن النجاح إلا بعد commit الصفحة الأخيرة.
  3. كل كتابة `INSERT … ON CONFLICT (store_id, external_id) DO UPDATE`، وروابط المنتج–التصنيف تُستبدل لتلك الصفحة فقط، فلا تكرار عند إعادة التشغيل.
  4. لا حذف تلقائي. يُحدَّث `last_seen_at` فقط، ويبقى الصف إن اختفى من القائمة.
  5. `metadata JSONB` صغير ومحدَّد (روابط/بيانات Salla الوصفية/العلامة)، ولا يعتمد عليه أي حكم في المجال.
- **البدائل:** معاملة واحدة للتشغيل كله — تُلغي كل التقدّم عند فشل الصفحة 17 وتُطيل القفل؛ حذف بالنقص — غير آمن بلا enumerator موثّق؛ تخزين الـ payload كاملًا — يحوّل قاعدة البيانات إلى JSON.
- **الأثر:** تشغيل فاشل يُبقي الصفحات المكتملة، وإعادة التشغيل آمنة، والذاكرة محدودة بحجم صفحة واحدة (30 عنصرًا).

## ADR-039 — قفل مزامنة بمُهلة، ترقيم تسلسلي، وسياسة إعادة محاولة محدودة

- **الحالة:** مقبول ومنفّذ
- **السياق:** طلبان متزامنان لنفس المتجر قد يضاعفان استهلاك حد Salla ويكتبان عدّادات متضاربة. كما أن أخطاء المزوّد ليست كلها مؤقتة، وإعادة المحاولة العمياء تُضاعف الحمل.
- **القرار:**
  1. جدول `sync_locks` بمفتاح `(store_id, resource)` وقيمة `lock_id` ومُهلة `expires_at`. الاستحواذ عبارة عن `INSERT … ON CONFLICT DO UPDATE … WHERE expires_at <= now()` ذرّية؛ الفائز واحد، والباقي يحصل على `409 CONFLICT` بسبب `sync_in_progress`. مورد القفل للكتالوج هو `catalog` ويُستحوذ عليه مرة واحدة للطلب كله (`categories`, `products`, أو `all`)، فلا تتزامن موارد المتجر الواحد.
  2. المُهلة 120 ثانية وتُجدَّد بعد كل صفحة؛ عامل متوقف يتيح الاستحواذ بعد انتهائها، و`lock_id` يمنع تحرير قفل مملوك لعامل آخر.
  3. `sync_runs` هو المصدر الوحيد لحالة المزامنة (`never/running/succeeded/failed`) و`last_success_at`؛ لا جدول حالة موازٍ يتعارض معه.
  4. إعادة المحاولة: شبكة، 429، 5xx فقط، بحد 3 محاولات، وتأخير أسّي أو `Retry-After` **بالقيمة نفسها**. إذا تجاوز `Retry-After` 30 ثانية يتوقف التشغيل بدل إعادة المحاولة مبكرًا. 400/401/403/404/422 ومخالفة المخطط لا تُعاد.
  5. 401 يُعالَج بمسار منفصل: تجديد واحد ثم إعادة الطلب مرة واحدة فقط؛ إن تكرر → `REAUTH_REQUIRED` مع وسم الاتصال.
  6. صلاحية جديدة `store:sync` (Owner/Admin/Manager) لأن بدء المزامنة عملية كتابة محلية، لا مجرد قراءة.
- **البدائل:** قفل في الذاكرة — لا يعمل عبر العمليات/النسخ؛ قفل استشاري في PostgreSQL — ممكن لكن لا يُظهر المُهلة في المراقبة؛ إعادة المحاولة على 4xx — تكرّر خطأ دائمًا.
- **الأثر:** 10 طلبات متزامنة على المورد نفسه تنتج تشغيلًا واحدًا وتسعة رفضات صريحة (مُختبر)، وطلب مورد آخر أثناء تشغيل جارٍ يُرفض بالقفل نفسه (مُختبر)، وكل تشغيل قابل للتتبع بـ `correlationId` و`syncRunId`.

## ADR-040 — توسيع السكوبات إلى قراءة المنتجات والتصنيفات، وعميل كتالوج معزول

- **الحالة:** مقبول ومنفّذ
- **السياق:** Phase 03 طلب `offline_access` فقط لأن الهوية تكفي من `user/info`. Phase 04 يحتاج `GET /products` و`GET /categories`، وكلاهما يتطلب سكوب قراءة مستقلًا. كما أن أي عميل عام يفتح الباب لاستدعاء نقاط كتابة.
- **القرار:**
  1. `SALLA_REQUIRED_SCOPES = ["offline_access", "products.read", "categories.read"]` — لا سكوبات كتابة ولا سكوبات لمراحل لاحقة.
  2. عميل `SallaCatalogClient` يحوي طريقتين فقط (`listProducts`, `listCategories`) ولا يملك وسيلة عامة لاستدعاء أي Endpoint آخر.
  3. الاتصال القائم الذي مُنح قبل التوسيع لا يُعتبر صالحًا للمزامنة: يُفحص `scopes` محليًا قبل بدء التشغيل، ويُعاد المستخدم إلى «إعادة الربط» برسالة صريحة (`missing_scope`) بدل فشل غامض عند Salla.
  4. نقطة API للكتالوج (`SALLA_API_URL`) قابلة للتجاوز في بيئات التطوير/الاختبار فقط، وتُرفض في الإنتاج عبر طبقة الإعداد الحالية.
- **البدائل:** طلب كل السكوبات مسبقًا — يخالف مبدأ الحد الأدنى؛ معالجة فشل السكوب عند Salla فقط — يستهلك محاولات ويُظهر خطأ تقنيًا للمستخدم.
- **الأثر:** كل متجر مربوط قبل Phase 04 يحتاج إعادة ربط واحدة، وهي خطوة مقصودة ومُعلنة في الواجهة، ولا تُخزَّن بيانات من متجر بلا السكوبين.

## ADR-041 — مطابقة الأصل (Origin) في CSRF خلف وكيل يعيد كتابة `Host`

- **الحالة:** مقبول ومنفّذ
- **السياق:** فحص CSRF يقارن أصل الطلب بـ `Host` الواصل. في بيئة المعاينة (وكيل TLS أمام التطبيق) يعيد الوكيل كتابة `Host` إلى عنوان المنبع، فيصل `Host: 127.0.0.1:4010` بينما `Origin` في المتصفح هو `https://4010-….e2b.app`، فيُرفض كل طلب كتابة (تسجيل الدخول، المزامنة) بـ 403 رغم أن الرمز المزدوج صحيح. رُصد ذلك فعليًا في المعاينة: طلبا دخول متتاليان بـ 403 مع تجديد الرمز بينهما.
- **القرار:**
  1. تُبنى قائمة المضيفين المقبولين من: `Host` الواصل، وأول قيمة في `x-forwarded-host` (يضبطها الوكيل المُنهي لـ TLS)، ومضيف `APP_URL` المضبوط. لا يُقرأ أي مضيف من جسم الطلب أو من قيمة يرسلها العميل.
  2. تُقارن المضيفات بعد تطبيعها (حروف صغيرة، شكل `host[:port]` فقط)؛ لا تُقبل قيم مشوّهة ولا بروتوكولات غير `http(s)`.
  3. في غير الإنتاج فقط، تُقبل أيضًا مضيفات `*.e2b.app` عبر https، لأن مضيف المعاينة يتغيّر لكل جلسة. الإنتاج لا يقبلها.
  4. يبقى الرمز المزدوج هو الضابط الأساسي؛ مطابقة الأصل طبقة دفاع إضافية.
  5. كل رفض يُسجَّل بـ `event: csrf.rejected` مع `reason` و`host`/`forwardedHost`/`sourceHost` و`hasCookie`/`hasHeader` — أسماء ونقاط نعم/لا فقط، بلا رموز أو كوكيز.
- **البدائل:** تعطيل الفحص في التطوير — يخفي العيب بدل إصلاحه ويُبقي الإنتاج بلا اختبار؛ الثقة بكل `x-forwarded-host` بلا تحقق — تقبل مضيفًا غير متوقع؛ الاعتماد على `Referer` وحده — يغيب في بعض الطلبات.
- **الأثر:** المعاينة تعمل خلف الوكيل، وطلب من أصل أجنبي يبقى مرفوضًا 403 (مُختبر)، والكود يشرح سبب القائمة بدل مقارنة مضيف واحدة هشّة.
