# Architecture Decision Records (ADRs)

> كل قرار قابل للتغيير، لكن ليس بصمت. أي تعديل يتطلب ADR جديدًا يشير إلى القديم.
>
> **التاريخ الموحّد للقرارات الأولية:** 2026-10-21

---

## ADR-001 — Modular Monolith بدل Microservices

- **الحالة:** مقبول
- **السياق:** مشروع جديد، فريق صغير، يتطلب معاملات متسقة بين الطلبات والمخزون والتحليلات.
- **القرار:** تطبيق Next.js واحد مقسّم إلى وحدات بحدود برمجية، مع Worker منفصل لاحقًا.
- **البدائل:** microservices (رفض: تكلفة تشغيل وتعقيد بيانات عالية)، monolith غير مقسم (رفض: يمنع الفصل المستقبلي).
- **النتائج:** سرعة تطوير، ACID، اختبارات أبسط. التكلفة: انضباط في الحدود يجب مراجعته.
- **إعادة النظر:** عند حاجة وحدة (مثل AI/SEO) إلى توسّع مستقل أو فريق منفصل.

## ADR-002 — Next.js 16 App Router

- **الحالة:** مقبول
- **السياق:** الحاجة إلى واجهة عربية RTL + API + نشر بسيط.
- **القرار:** Next.js 16.4.2 / React 19.3.1 / App Router.
- **البدائل:** SPA + API منفصل (رفض: تعقيد تشغيلي مبكر)، Remix/Astro (رفض: نظام أقل ملاءمة للوحات التفاعلية لاحقًا).
- **النتائج:** RSC يقلل JS، route handlers للـ API، وبيئة معروفة. التكلفة: ارتباط بإيقاع Next.
- **إعادة النظر:** لا متوقع قبل Phase 24.

## ADR-003 — TypeScript 5.9 بدل 7.x

- **الحالة:** مقبول (مؤقت)
- **السياق:** TypeScript 7 متاح، لكن `typescript-eslint` 8.72 يقيّد `<6.1.0`.
- **القرار:** تثبيت `typescript ~5.9.3`.
- **البدائل:** TS 7 بلا ESLint (رفض: فقدان بوابة الجودة).
- **النتائج:** توافق كامل. التكلفة: تأخر ميزات لغوية.
- **إعادة النظر:** عند دعم `typescript-eslint` لـ TS 7.

## ADR-004 — PostgreSQL + Drizzle ORM

- **الحالة:** مقبول (تنفيذ Phase 02)
- **السياق:** بيانات علائقية، JSONB للأحداث، تحليلات، عزل RLS.
- **القرار:** PostgreSQL 16 + Drizzle ORM + Drizzle Kit.
- **البدائل:** Prisma (رفض: محرّك/codegen، وSQL أقل شفافية، وتعقيد نشر)، MongoDB (رفض: علاقات وتقارير)، raw SQL فقط (رفض: سرعة تطوير أقل).
- **النتائج:** SQL صريح، هجرات مقروءة، دعم RLS، بلا محرّك أصلي.
- **إعادة النظر:** لا متوقع.

## ADR-005 — تعدد المستأجرين من اليوم الأول

- **الحالة:** مقبول
- **السياق:** المشروع يبدأ بمتجر واحد (كشخة) لكنه SaaS.
- **القرار:** `User → Organization → Store → SallaConnection` من أول مخطط قاعدة بيانات. متجر واحد لكل مؤسسة الآن، والتصميم يسمح بعدة متاجر.
- **البدائل:** `store_id` مباشر على المستخدم (رفض: يعيد بناء النظام لاحقًا).
- **النتائج:** تعقيد بسيط الآن، عزل حقيقي لاحقًا.

## ADR-006 — لا `store_id` من العميل كدليل صلاحية

- **الحالة:** مقبول
- **السياق:** أشهر ثغرة في SaaS متعدد المستأجرين هي IDOR.
- **القرار:** تحديد المتجر من الجلسة → العضوية → الصلاحية → UUID داخلي. قيمة العميل «طلب» فقط.
- **النتائج:** كل use case يستقبل `TenantContext` إلزاميًا. التكلفة: boilerplate مقصود.
- **الاختبار:** مصفوفة عزل لكل مسار كتابة/قراءة.

---

## ADR-007 — جلسات مخصّصة Opaque بدل Auth.js Credentials

- **الحالة:** مقبول (تنفيذ Phase 02)
- **السياق:** نحتاج إبطالًا فوريًا، سياق مستأجر واضحًا، ومسار SSO مستقبلًا. Auth.js مع Credentials provider يقيّد جلسات قاعدة البيانات.
- **القرار:** جلسات opaque 256-bit مخزّنة SHA-256 في `sessions`، كوكي `__Host-*`، `scrypt` لكلمات المرور، وتدوير/إبطال كامل.
- **البدائل:** Auth.js + JWT (رفض: إبطال أصعب)، Auth.js + DB sessions مع Credentials (رفض: قيود معروفة)، Clerk/Auth0 (رفض: تكلفة واعتماد خارجي مبكر).
- **النتائج:** تحكم كامل وقابلية اختبار. التكلفة: نحن مسؤولون عن أمان المصادقة؛ تُخفَّف بمراجعة أمنية واختبارات ASVS.
- **إعادة النظر:** عند إضافة SSO/Social login.

## ADR-008 — Salla Custom Mode OAuth مع `state`

- **الحالة:** مقبول مبدئيًا — يتطلب تأكيدًا في Phase 03
- **السياق:** نريد ربط المتجر بمؤسسة محددة يبدأها مستخدم مصادق.
- **القرار:** Custom Mode (authorization code) + `state` مرتبط بالجلسة والمؤسسة، مع تخزين الرموز مشفّرة.
- **البدائل:** Easy Mode عبر `app.store.authorize` (يُعاد تقييمه إن اشترطته Salla للنشر).
- **النتائج:** تحكم بالربط. التكلفة: إدارة تجديد الرموز بأنفسنا.
- **إعادة النظر:** بعد قراءة متطلبات Salla Partners الفعلية.

## ADR-009 — سياسة «لا Endpoint بلا وثيقة»

- **الحالة:** مقبول
- **السياق:** ممنوع اختراع Salla API أو Scopes.
- **القرار:** كل Endpoint/Scope يُستخدم يُسجّل في `salla-reference.md` مع method + path + scope + رابط + تاريخ تحقق. لا كود تكامل قبل التسجيل.
- **النتائج:** بطء بسيط مقابل دقة. أي معلومة غير مؤكدة تُعلَّم صريحًا.

---

## ADR-010 — تشفير رموز Salla + تجديد Single-Flight

- **الحالة:** مقبول (تنفيذ Phase 03)
- **السياق:** رموز Salla تمنح وصولًا لمتجر كامل، والـ refresh أحادي الاستخدام.
- **القرار:** AES-256-GCM مع IV فريد وAAD = `store_id` و`key_version`، تجديد استباقي داخل قفل صفّي/موزّع، ومنع التجديد المتوازي.
- **النتائج:** تقليل خطر سرقة الرموز وإبطال الاتصال. التكلفة: تعقيد تشغيلي ودوران مفاتيح.

---

## ADR-011 — طبقة AI مستقلة عن المزوّد

- **الحالة:** مقبول ومنفّذ (العقد فقط)
- **السياق:** لا نريد الارتباط بـ OpenAI أو غيرها.
- **القرار:** `AiProvider` + `AiProviderRegistry` + `AiGateway`، ولا مزوّد في Phase 01.
- **النتائج:** استبدال المزوّد لاحقًا دون تغيير المجال. التكلفة: طبقة وسيطة إضافية.

---

## ADR-012 — AI لا يكتب أبدًا

- **الحالة:** مقبول
- **السياق:** مخاطر مالية/سمعية عند تنفيذ مخرجات نموذجية.
- **القرار:** AI ينتج اقتراحًا فقط. Action Engine هو الكاتب الوحيد، بعد موافقة، مع تحقق وقياس.
- **النتائج:** أمان وحوكمة. التكلفة: خطوة بشرية إضافية مقصودة.

---

## ADR-013 — مخرجات منظمة + إصلاح محدود

- **الحالة:** مقبول ومنفّذ
- **السياق:** النماذج تُنتج JSON غير صالح أو حقولًا ناقصة.
- **القرار:** Zod schema لكل مهمة، تحقق إلزامي، رسالة إصلاح واحدة كحد افتراضي، ثم `AI_INVALID_OUTPUT`.
- **النتائج:** لا تمر مخرجات غير متحققة إلى منطق العمل.

## ADR-014 — الأحداث At-least-once + Dedupe

- **الحالة:** مقبول (تنفيذ Phase 06)
- **السياق:** Salla تعيد المحاولة، والشبكة قد تكرر.
- **القرار:** تخزين خام، dedupe فريد، معالجة idempotent، DLQ.
- **النتائج:** لا فقدان ولا تكرار مؤثر. التكلفة: كل handler يجب أن يكون idempotent.

## ADR-015 — تأجيل Queue واختيارها عبر Port

- **الحالة:** مقبول
- **السياق:** Redis/BullMQ بنية إضافية، ولا حاجة قبل Phase 06.
- **القرار:** تعريف `JobQueue` port الآن تصميمًا، واختيار pg-boss (Postgres) أو BullMQ في Phase 06 حسب الحمل.
- **النتائج:** تجنّب بنية غير ضرورية مع مرونة.

## ADR-016 — العربية أولًا وRTL

- **الحالة:** مقبول
- **السياق:** الجمهور الأساسي سعودي، والتصميم الغربي الافتراضي ينتج تجربة ركيكة.
- **القرار:** `dir="rtl"` و`lang="ar"` من الجذر، خطوط نظامية، خصائص CSS منطقية، عزل النصوص اللاتينية.
- **النتائج:** تجربة أصلية. التكلفة: الإنجليزية تتطلب لاحقًا i18n منظمًا.

## ADR-017 — لا بيانات وهمية في واجهة الإنتاج

- **الحالة:** مقبول

- **النتائج:** صدق قابل للتحقق.

## ADR-020 — Phase 01 بلا قاعدة بيانات أو مخطط

## ADR-021 — تقليل PII وسياسة السجلات

- **الحالة:** مقبول
- **السياق:** بيانات العملاء حسّاسة قانونيًا.
- **القرار:** تخزين الحد الأدنى، تنقية السجلات، منع المحتوى الخام في logs، احتفاظ محدود.

## ADR-022 — استراتيجية الاختبار

- **الحالة:** مقبول
- **السياق:** لا يمكن بناء نظام مالي/تشغيلي بلا اختبارات.
- **القرار:** Unit (Vitest)، Integration (Postgres)، Contract (Salla fixtures/Demo Store)، E2E (Playwright من Phase 02/15)، Security tests من Phase 02، AI evals من Phase 14.
- **النتائج:** ثقة تدريجية. التكلفة: وقت CI.

## ADR-023 — نشر محايد للمنصة

- **الحالة:** مقبول
- **السياق:** لا اختيار منصة نهائي.
- **القرار:** صورة حاوية للتطبيق + Worker + Postgres مُدار. Vercel ممكن للواجهة لاحقًا لكنه ليس افتراضًا معماريًا.
- **النتائج:** مرونة. التكلفة: لا استفادة من ميزات منصة محددة الآن.

- **النتائج:** قابلية مقارنة وتفسير.

## ADR-026 — سياسة بيانات المنافسين

- **الحالة:** مقبول
- **السياق:** جمع بيانات المنافسين قد يخالف القانون/الشروط.
- **القرار:** مصادر عامة أو مرخّصة فقط، احترام robots/ToS، لا تجاوز حماية، تسجيل المصدر والتاريخ، مراجعة قانونية قبل Phase 13.
- **النتائج:** مخاطر قانونية أقل. التكلفة: تغطية بيانات أقل.

---

## ADR-027 — لا أسرار في المستودع + بوابة فحص

- **الحالة:** مقبول ومنفّذ
- **السياق:** تسريب مفتاح واحد قد يكشف متاجر.
- **القرار:** `.env.example` فقط، `.gitignore` يمنع `.env*`، `npm run check:secrets` في CI، تنقية السجلات.
- **النتائج:** تقليل خطر التسريب. التكلفة: إدارة أسرار منفصلة لكل بيئة.

## ADR-028 — Node.js 22 LTS

- **الحالة:** مقبول
- **السياق:** Next 16 وVitest يدعمان Node 22+.
- **القرار:** `engines >=22` و`.nvmrc=22`.
- **النتائج:** توافق مع `AbortSignal.any/timeout` وWeb APIs.
